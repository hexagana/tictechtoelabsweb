Topic 1

Getting Started: Importing and Exploring Your Data

This section walks you through everything you need to get your sample data into Power BI Desktop and verify that it is structured correctly before you write a single DAX formula. Taking the time to import your tables carefully and confirm that relationships exist between them means your calculations will work reliably later.

By the end of this section, you will have three tables loaded into Power BI, a complete data model with all necessary relationships in place, and a clear picture of what each table contains.

What you need before you begin

Before opening Power BI Desktop, make sure you have the following ready:

  • Power BI Desktop installed on your computer
  • The three sample Excel workbooks provided in the course description: Cookie Types, Customers, and Orders (see Practice files)
NoteIf you are new to Power BI or would like a general refresher before diving into DAX, watch the introductory video linked in the course description. It covers the foundational concepts that this guide builds on.

DAX stands for Data Analysis Expressions. It is a formula language built into Power BI that uses functions similar to those found in Microsoft Excel. If you have ever written an Excel formula, many of the patterns you already know will transfer directly.

Opening Power BI Desktop and starting your first import

Once Power BI Desktop is open, you will see the main welcome screen. This screen provides several quick-start options, including a dedicated shortcut for bringing in Excel data.

  1. On the main screen, locate the Add data to your report section.
  2. Click Import data from Excel.

This opens the Windows File Picker dialog, which lets you browse to wherever you saved the sample workbooks.

  1. Navigate to the folder containing your sample data files.
  2. Select the Cookie Types workbook and click Open.

Selecting and loading the Cookie Types table

After you click Open, Power BI displays the Navigator window. This window lists every sheet and named table found inside the workbook, and it shows you a live data preview so you can verify you are loading the right content.

  1. In the Navigator window, select the sheet named cookie types.
  2. Review the data preview to confirm the columns and rows look correct.
  3. Click Load to import the data into your report.

Once the load completes, you will see the Cookie Types table appear in the Fields pane on the right side of the screen. This confirms the import was successful.

Importing the Customers and Orders workbooks

With Cookie Types loaded, you will now bring in the remaining two workbooks using the Excel button in the top ribbon. This button is the standard way to add more data sources after your initial import.

  1. In the Home tab of the top ribbon, click Excel.
  1. Select the Customers workbook and click Open.
  2. In the Navigator window, select the Customers sheet, review the preview, and click Load.
  1. Click Excel in the ribbon again.
  2. Select the Orders workbook, click Open, select the Orders sheet in the Navigator, and click Load.

After completing these steps, all three tables (Cookie Types, Customers, and Orders) should be listed in the Fields pane. Take a moment to confirm all three names appear before moving on.

TipIf a table does not appear in the Fields pane, repeat the import steps for that workbook. Check that you selected the correct sheet in the Navigator before clicking Load.

Reviewing what each table contains

Now that your data is loaded, it is worth spending a moment in the Data view to understand exactly what information each table holds. This context will make your DAX formulas much easier to reason about.

Click the Data view icon on the left-hand sidebar to switch out of the report canvas and into a row-by-row view of your tables.

The Orders table

Select the Orders table. This is the central table in your data model: it records every individual transaction and contains the following columns:

  • Customer ID: links each order back to a specific customer
  • Order ID: a unique identifier for each order
  • Product: the name of the cookie type ordered
  • Units Sold: how many units were sold in that order
  • Date: the date the order was placed
  • Revenue: the total revenue generated by the order
  • Cost: the total cost associated with the order

Verifying and completing your data model

Having all three tables loaded is only half the job. Before you can write DAX measures that span multiple tables, Power BI needs to know how those tables relate to one another. Click the data model icon on the left sidebar to open the model view.

Confirming the Customers–Orders relationship

Power BI should have automatically detected and created a relationship between the Orders table and the Customers table using the shared Customer ID field. This is a one-to-many relationship, meaning each customer can appear in many different orders.

Confirm that this relationship line is visible between the two tables in the diagram before continuing.

Creating the missing Cookie Types–Orders relationship

You will likely notice that no relationship yet exists between the Cookie Types table and the Orders table. This gap needs to be filled manually. The connecting fields are:

  • Cookie Type in the Cookie Types table
  • Product in the Orders table

These two fields contain the same values (the name of each cookie) even though they have different column names.

To create the relationship:

  1. In the model view, click and drag the Cookie Type field from the Cookie Types table onto the Product field in the Orders table.

This establishes a one-to-many relationship between the two tables: each cookie type can appear across many individual orders.

Understanding the role of each table

With all relationships in place, your data model follows a clear structure:

  • Orders is the central fact table. It contains every transaction record, including revenue and cost figures.
  • Customers and Cookie Types are lookup tables. They provide supporting detail, such as customer contact information and per-cookie pricing, that enriches the Orders data.

This structure is the foundation that allows DAX measures to filter, aggregate, and cross-reference data across all three tables at once.

Returning to the report view

Once you have confirmed that all relationships are correct and the model is arranged as you want it, you are ready to move on to building calculations.

  1. Click the report icon on the left sidebar to return to the report canvas.

The canvas will display the message: "Build visuals with your data. Select or drag fields from the Fields pane onto the report canvas." This is your blank workspace for adding visuals and the DAX measures you will create next.

A measure in Power BI is a calculation that runs dynamically across your entire data model. Rather than computing a value for a single row, a measure evaluates across all relevant rows based on the context of whatever visual or filter is currently active. For example, a measure that sums the Units Sold column will give you the total number of cookies sold across all orders, and that total will automatically adjust when you slice the data by date, customer, or cookie type.

That's everything you need to get your data into Power BI and confirm it is properly connected. Your three tables are loaded, your relationships are established, and your report canvas is ready. You are now fully prepared to start writing DAX formulas.

Topic 2

Building Essential Measures: Units Sold and Customer Analysis

With your data model in place, you can begin building the measures that will power your analysis. Measures are calculated fields that aggregate, count, or transform your data dynamically based on the context of any visualization you place them in.

This section walks you through creating three foundational measures: Total Number of Units Sold, Count of orders, and Distinct Customers. Each measure builds on the same workflow, so mastering the first one makes every subsequent measure faster and more intuitive to create.

By the end of this section, you will have a working set of measures that reveal how many units your business has sold, how many orders have been placed, and how many unique customers you serve, all ready to use in any report visualization.

Creating the Total Number of Units Sold measure

The Total Number of Units Sold measure uses the DAX SUM function to add up every value in the Units Sold column of the Orders table. This is one of the most commonly used measure patterns in Power BI and serves as an excellent starting point for understanding how measures work.

Step 1 — Open the New Measure dialog

  • In the Fields pane on the right side of the Power BI Desktop interface, locate the Orders table.
  • Hover over the Orders table to reveal the options icon, then right-click the table name to open the context menu.
  • At the top of the context menu, select New measure.

Step 2 — Review the Measure tools tab

  • After selecting New measure, Power BI activates the Measure tools tab in the ribbon.
  • The formula bar appears at the top of the report canvas.
  • By default, the formula bar displays Measure =.
  • The Name field in the Measure tools tab shows "Measure" as a placeholder.

Step 3 — Name the measure

  • Click inside the formula bar to position your cursor.
  • Delete the default placeholder text "Measure".
  • Replace it with a clear, descriptive name.
Total Number of Units Sold

The formula bar should now read: Total Number of Units Sold =

  • Using a descriptive name from the start is a best practice.
  • When your model contains dozens of measures, clear names make it much easier to locate the right measure in the Fields pane.
  • Clear names help you understand each measure's purpose at a glance.

Step 4 — Enter the SUM function using IntelliSense

  • After the equals sign, begin typing sum.
  • As you type, Power BI's IntelliSense engine displays a dropdown list of matching DAX functions, each accompanied by a brief description.
  • This auto-complete feature helps you find the right function quickly and reduces the chance of typing errors.
  • Select SUM from the IntelliSense dropdown.
  • The SUM function adds all numeric values in a specified column.

Step 5 — Specify the column

  • After selecting SUM, type an opening parenthesis (
  • Power BI immediately displays a list of available tables and columns.
  • Scroll through the list to locate the Orders table.
  • Select the Units Sold column.

Your completed formula should read:

Total Number of Units Sold = sum(Orders[Units Sold])

Before committing, take a moment to verify three things:

  • The measure name is descriptive and accurate.
  • The SUM function is used.
  • The correct table and column are referenced: Orders[Units Sold].

Committing the measure and verifying it in the Fields pane

Once your formula is complete, you need to commit it properly so Power BI saves the measure to your model. Pressing Enter or clicking the checkmark (commit) icon in the formula bar both accomplish this, but it is important not to simply click away from the formula bar without committing, as unsaved changes can be lost.

Step 1 — Commit the measure

  • Click the checkmark (commit) icon located to the left of the formula bar, or press Enter on your keyboard.
  • The formula bar should display:
Total Number of Units Sold = sum(Orders[Units Sold])

Step 2 — Verify the measure in the Fields pane

  • After committing, look at the Fields pane on the right side of the screen.
  • Expand the Orders table and confirm that Total Number of Units Sold now appears in the list.
  • Measures are distinguished from regular columns by a small calculator icon displayed next to their name.
  • Seeing the measure listed here confirms it has been saved to the model.
  • The measure is available for use in any visualization across your report.

Adding the measure to a visualization and formatting the output

With the measure created and committed, the next step is to place it in a visualization and ensure the values display in a meaningful format.

Step 1 — Add the measure to the report canvas

Click the checkbox next to Total Number of Units Sold in the Fields pane. Power BI adds the measure to the report canvas as a default visualization.

Step 2 — Switch to a matrix visualization

For a clearer table-style view of the data, click the matrix icon in the Visualizations pane. The matrix displays the total number of units sold as a single aggregated value: in this dataset, 1,125,806.

The Filters, Visualizations, and Fields panes on the right side of the interface allow you to refine the visual further. You will see that Total Number of Units Sold is now listed in the Values area of the Visualizations pane.

Step 3 — Break down units sold by customer

To see how units sold are distributed across customers, drag the Name field from the Customers table into the Rows area of the matrix. The matrix now displays a row for each customer alongside their total units sold, with a grand total at the bottom. Example customers include ABC Groceries, ACME Bites, Park & Shop Convenience Stores, Tres Delicious, and Wholesome Foods.

Step 4 — Identify and fix the decimal formatting issue

You may notice that the totals display decimal places, for example 221,023.00. Since this dataset tracks cookies sold in whole units, decimal values are not meaningful and are likely the result of a data entry error somewhere in the source data.

NoteFormatting changes applied to a measure persist across all visualizations that use that measure. You only need to set the format once.

To fix this, click on Total Number of Units Sold in the Fields pane to select it. In the Measure tools tab that appears in the ribbon, locate the decimal places dropdown; it defaults to Auto.

Set the decimal places value to 0.

The matrix immediately updates to show whole numbers only, such as 221,023.

Step 5 — Verify that formatting persists across new visuals

To confirm the formatting is stored in the measure itself (not just the current visual), delete the matrix from the canvas and add a new matrix visualization. Drag Total Number of Units Sold back into the Values area. The whole-number formatting is retained automatically.

This behavior confirms that formatting is a property of the measure, not the visual, which is one of the key advantages of using measures over ad-hoc aggregations.

Editing and removing measures when needed

Power BI makes it straightforward to revise or remove measures as your analysis evolves. You can return to the formula bar at any time to update the measure's name, formula, or formatting.

Editing a measure name

Click on a measure in the Fields pane to select it. The formula bar becomes active and displays the current name and formula. You can edit the name directly in the formula bar, for example changing "Units" to "Cookies" to reflect the specific product your business sells.

Deleting a measure

If a measure is no longer needed, select it in the Fields pane and press the Delete key. The measure is removed from the model entirely.

WarningDeleting a measure removes it permanently from the model. Any visuals that rely on the deleted measure will display an error. Confirm that no active visuals depend on a measure before deleting it.

In this workflow, you may need to remove a practice or renamed measure before moving on to build the next set of measures. Keeping your Fields pane clean and free of unused measures makes your model easier to navigate and maintain.

Building the Count of Orders measure

With the units sold measure complete, you can now apply the same workflow to count the number of orders in the dataset. Where the previous measure used SUM to aggregate a numeric column, this measure uses COUNTROWS to count the number of rows in the Orders table, where each row represents one order.

Step 1 — Confirm the starting state

Before creating the next measure, confirm that the report canvas shows the card visual for the measure you just created; in this example, Total Number of Cookies Sold with a value of 1,125,806. This confirms your previous work is intact.

You can also switch to the Data view to inspect the Orders table directly. The table contains columns for Customer ID, Order ID, Product, Units Sold, Date, Revenue, and Cost, and includes 700 rows in total. Each row represents a single order.

Step 2 — Return to Report view and create the new measure

Click the report icon on the left sidebar to switch back to the report canvas. Right-click the Orders table in the Fields pane and select New measure.

The formula bar opens with the default placeholder Measure =.

Step 3 — Name the measure and enter the formula

Replace the placeholder with the measure name:

Count of orders =

After the equals sign, begin typing count. From the IntelliSense dropdown, select COUNTROWS. The COUNTROWS function counts the number of rows in a specified table; in this case, each row in the Orders table corresponds to one order.

Inside the parentheses, type Orders as the table name. Your complete formula should read:

Count of orders = COUNTROWS(Orders)

Commit the measure by clicking the checkmark icon or pressing Enter.

Step 4 — Verify and visualize the result

After committing, confirm that Count of orders appears under the Orders table in the Fields pane.

Drag the Count of orders measure onto the report canvas. A card visual appears displaying the value 700, which matches the 700 rows you observed in the data view.

TipCross-checking your measure result against a known value, such as the row count in the data view, is a reliable way to confirm your measure is working correctly.

Step 5 — Break down order counts by customer

Add the Name field from the Customers table to the Rows area. The visual now shows each customer's individual order count:

Building the Distinct Customers measure

The order count measure tells you how many orders exist, but it does not tell you how many unique customers placed those orders. The same customer can appear in many rows of the Orders table. To find the number of distinct customers, you use the DISTINCTCOUNT function, which counts only unique values in a column.

Step 1 — Create the new measure

In the Fields pane, right-click the Orders table and select New measure. In the formula bar, type the measure name:

Distinct Customers =

Step 2 — Enter the DISTINCTCOUNT function

After the equals sign, begin typing dist. From the IntelliSense dropdown, select DISTINCTCOUNT. The DISTINCTCOUNT function counts the number of distinct (unique) values in a specified column.

Step 3 — Specify the column

Inside the parentheses, select the column you want to count unique values from. In this case, choose Orders[Customer ID] to count the number of unique customer IDs present in the Orders table.

Your complete formula should read:

Distinct Customers = DISTINCTCOUNT(Orders[Customer ID])

Close the parentheses and commit the measure by pressing Enter or clicking the checkmark icon.

Verifying the Distinct Customers result and adding documentation

After committing, confirm that the Distinct Customers measure appears under the Orders table in the Fields pane.

A card visual on the report canvas displays Distinct Customers with a value of 5. This confirms there are five unique customers in the dataset, consistent with the five customer names visible in the earlier matrices.

This result makes intuitive sense: even though there are 700 orders in the table, all of those orders were placed by just 5 distinct customers.

Adding comments to your measure

DAX supports inline comments, which are a practical way to document the purpose of each measure directly in the formula. Comments do not affect the calculation in any way; they are purely informational.

To add a comment to the Distinct Customers measure:

  1. Click on Distinct Customers in the Fields pane to open it in the formula bar.
  2. Press Shift + Enter to add a new line within the formula.
  3. On the new line, type your comment preceded by //, for example:
// This tells me how many customers we have
TipAdding comments is especially valuable when you share reports with colleagues or return to a model after a period of time. A one-line comment explaining what each measure calculates saves significant time when reviewing or troubleshooting a model.

Commit the updated measure. The card visual continues to display the value 5, confirming that the comment has no effect on the calculation.

Reviewing your measures and preparing for profit calculations

At this point, your report canvas displays the Distinct Customers card and the customer order count table side by side. Together, these measures give you a clear picture of customer activity across your dataset.

Before moving on, it is useful to switch to the Data view once more to examine the Revenue and Cost columns in the Orders table. These two columns will form the basis of the next measure you build.

The approach for calculating total profit follows the same pattern you have already used: sum the Revenue column, sum the Cost column, and subtract the second from the first. Understanding how the data is structured in these columns makes it straightforward to write that formula confidently.

You now have three working measures (Total Number of Units Sold, Count of orders, and Distinct Customers), each documented, formatted, and verified against the underlying data. These measures form a solid analytical foundation and demonstrate the three most common DAX aggregation patterns: summing a numeric column, counting rows in a table, and counting distinct values in a column. You're ready to move on to building measures that use operators to combine aggregations, starting with total profit.

Topic 3

Advanced Calculations: Profit Analysis and Margin Metrics

Understanding profitability is one of the most common goals in business reporting, and Power BI Desktop provides several complementary approaches to achieve it.

This section walks you through three progressively sophisticated techniques: calculating basic profit using measures and calculated columns, building and formatting a profit margin percentage measure, and leveraging iterator functions to compute row-level profit across a summary table. By working through each technique in order, you'll develop a clear understanding of when to use each approach and how they differ in both behavior and performance impact.

Calculating profit using measures and calculated columns

Before building any visual, ensure your data model includes:

  • Orders table with at least a Revenue column and a Cost column
  • Customers table with a Name field

These are the foundation for all profit calculations in this section.

To add profit fields to a table visual:

  1. Start in the Report view.
  2. In the Fields pane, expand the Customers table and select the Name field to populate a table visual with customer names.
  3. Add Distinct Customers and Total Profit to the Values well of the visualization.

The table visual will now display each customer alongside their distinct customer count and total profit figure. Based on the sample data, results look like this:

CustomerDistinct CustomersTotal Profit
ABC Groceries1523,317.00
ACME Bites1828,379.00
Park & Shop Convenience Stores1423,498.50
Tres Delicious1302,199.00
Wholesome Foods1639,677.00
Total2,717,070.50

The underlying DAX formula for Total Profit aggregates revenue and cost across all rows before subtracting:

SUM(Orders[Revenue]) - SUM(Orders[Cost])

Creating a profit measure with Quick Measures

Power BI's Quick Measures tool lets you build DAX formulas through a guided interface without writing code from scratch.

  1. Navigate to Home > Calculations > Quick measure to open the dialog.
  1. In the Calculation dropdown, scroll to Mathematical operations and select Subtraction.
  1. Configure the fields by dragging Sum of Revenue from the Orders table into the Base value slot, and Sum of Cost into the Value to subtract slot.
  1. Click OK. Power BI creates a new measure called Revenue minus Cost and adds it to the Fields list. The generated DAX formula is:
Revenue minus Cost = SUM('Orders'[Revenue]) - SUM('Orders'[Cost])

Verifying the measure output

  • Add Revenue minus Cost to your existing table visual.
  • Compare the Revenue minus Cost column against the Total Profit column.
  • Both columns should display identical values for every customer and the overall total.
  • This confirms that the Quick Measures approach produces the same result as a manually written formula.
  • You can inspect the formula at any time by selecting the measure in the Fields pane and reading the expression in the formula bar.
  • Measures aggregate data dynamically based on the current filter context.

Creating a Profit calculated column

When you need a profit value stored for each individual order row (for example, to use in further row-level calculations or to filter by individual transaction profitability), a calculated column is the right choice.

  1. Switch to Data view by clicking the table icon in the left sidebar.
  2. The Orders table should display columns including Customer ID, Order ID, Product, Units Sold, Date, Revenue, and Cost.

Under Column tools, click New column. In the formula bar, enter:

Profit = Orders[Revenue] - Orders[Cost]
  • Power BI auto-completes column names as you type.
  • Press Enter to commit the formula.
  • The new Profit column appears immediately in the table, showing a calculated value for every row, for example 876, 2922, 7554, and so on.

Choosing between measures and calculated columns

Both approaches produce profit figures, but they serve different purposes and have different implications for your data model.

ApproachHow it behaves
MeasuresCalculated on the fly at query time and do not consume additional storage in the model. They respond dynamically to slicers, filters, and visual context.
Calculated columnsComputed at data refresh time and stored within the model, which increases its size. They are evaluated row by row and can be used in relationships, as filter values, or as inputs to further row-level logic.
NoteFor large datasets, prefer measures over calculated columns wherever possible to keep your data model lean and queries fast.

Creating and formatting a profit margin measure

Profit in absolute dollar terms tells you how much you're earning, but profit margin expresses that figure as a proportion of revenue, making it far easier to compare performance across products, regions, or time periods with different sales volumes.

Defining the profit margin percentage formula

  1. Return to Report view.
  2. In the Fields pane, right-click the Orders table and select New measure.
  3. The formula bar appears at the top of the canvas, ready for input.

Enter the following DAX formula:

Profit Margin % = [Total Profit] / SUM('Orders'[Revenue])
  • The [Total Profit] measure references the existing calculation you created earlier.
  • SUM('Orders'[Revenue]) calculates the total revenue in the current filter context.
  • Dividing one by the other gives you a decimal representing the proportion of revenue retained as profit.

Adding the measure to a matrix visual

NoteBecause [Total Profit] is itself a measure, Power BI resolves it correctly within any filter context, including when the formula is used inside a matrix broken down by product category.
  1. Insert a new matrix visual on the report canvas.
  2. Drag Cookie Type to the Rows field.
  3. Drag Profit Margin % to the Values field.
  4. The matrix now shows a decimal profit margin value for each cookie type.

Decimals like 0.60 are technically correct but harder to read at a glance. The next step converts these into properly formatted percentages.

Formatting the measure as a percentage

  1. Select the Profit Margin % measure in the Fields pane.
  2. In the formatting toolbar above the formula bar, change the format from General to Percentage.
  3. The matrix immediately updates to display readable percentage values.

Interpreting the results

TipAlways format percentage measures at the measure level rather than at the visual level. Formatting applied to the measure travels with it to every visual where it's used, ensuring consistency across your entire report.

With formatting applied, you can now compare profit margins across cookie types directly. In this example:

  • Snickerdoodle: 62.50%
  • Chocolate Chip: 60.00%
  • Overall total across all cookie types: 57.93%

These figures make it immediately clear which products are most profitable relative to their revenue, something that raw profit figures alone cannot easily convey. A product with high total profit but low margin may be generating most of its returns through volume, while a high-margin product might be constrained by limited sales.

Calculating total profit using iterator functions

The measures covered so far use standard aggregation functions like SUM, which operate over entire columns. These work well when your profit values are already stored in the data model. However, some data structures, particularly summary tables, store the components of profit rather than profit itself, requiring a row-by-row calculation before aggregation. This is where iterator functions come in.

Understanding the Cookie Types table structure

The Cookie Types table is a summary table that does not contain a pre-calculated profit column. Instead, it stores the inputs needed to derive profit at the row level.

The table contains the following columns and sample data:

Cookie TypeUnits SoldRevenue Per CookieCost Per Cookie
Chocolate Chip338,239.552
Fortune Cookie154,19810.5
Oatmeal Raisin155,31552.2
Snickerdoodle146,84641.5
Sugar168,78331.25
White Chocolate Macadamia Nut162,424.562.75

To calculate total profit from this table, you need to compute:

  • Calculate Units Sold * (Revenue Per Cookie - Cost Per Cookie) for every row, then sum those results. A standard SUM function cannot do this because there is no single column to sum; the profit must be derived on a per-row basis first.
  • The SUMX iterator function is designed exactly for this scenario.

How SUMX works

SUMX takes two arguments: a table and an expression. It iterates through each row of the specified table, evaluates the expression in the context of that row, and then sums all the results. Its syntax is:

SUMX(Table, Expression)

This row-by-row evaluation is what makes iterator functions more flexible than standard aggregators when working with tables that store per-unit metrics.

Writing the SUMX measure

  1. In the Fields pane, right-click and select New measure. In the formula bar, type the following:
Total Profit 2 = SUMX('Cookie Types', 'Cookie Types'[Units Sold] *
    ('Cookie Types'[Revenue Per Cookie] - 'Cookie Types'[Cost Per Cookie]))
  • As you type, Power BI displays a tooltip describing the SUMX syntax and auto-completes column names from the Cookie Types table, making it easier to build the expression accurately.
  • The expression inside SUMX first subtracts the cost per cookie from the revenue per cookie to get the profit margin per unit.
  • It then multiplies this margin by units sold to calculate the total profit contribution for that cookie type.
  • SUMX repeats this calculation for every row and sums the results.

Viewing and validating the result

After committing the formula, add Total Profit 2 to a card visual on the report canvas. The calculated result is 2,717,064.38.

NoteThe Total Profit 2 result of 2,717,064.38 is close to but not identical to the Total Profit figure of 2,717,070.50 calculated from the Orders table. This is expected: the two measures operate on different source tables with potentially different levels of rounding or data precision.

Aggregate vs. iterator functions: when to use each

Both aggregator functions (like SUM) and iterator functions (like SUMX) are valuable tools in DAX. Understanding the difference helps you choose the right approach for each scenario.

  • Use aggregator functions like SUM when you need to total values that already exist as a column in your data. They are simpler to write and slightly more efficient for straightforward totals.
  • Use iterator functions like SUMX when your calculation requires evaluating an expression row by row before aggregating, for example when multiplying per-unit values by quantities stored in the same table, or when applying conditional logic at the row level.

The idea in simple terms

  • Normal SUM
    • Adds up one column.
    • Example: add all the sales amounts.
  • SUMX
    • Works row by row, does a calculation for each row first, then adds up the results.
    • Use it when each row needs math, not just adding numbers.
Easy way to remember
  • SUM = add column
  • SUMX = calculate per row, then add

Why SUMX is perfect here

Each product row needs:

  • Price × Quantity
  • Then add all rows together
  • This is exactly what SUMX is meant for.

In many cases, both approaches will produce the same final number. The key distinction is the source data structure: if the value you want to sum doesn't exist yet as a column, an iterator function gives you the flexibility to calculate it on the fly during aggregation.

Topic 4

Time Intelligence and Date-Based Analysis

Understanding when things happen is just as important as understanding what happened. Power BI's date and time functions let you slice your data by day, week, month, or any other time unit, unlocking patterns that would otherwise stay hidden in a flat table of rows.

In this section, you'll learn how to work with the date functions available in Power BI's DAX formula language, create a calculated column that identifies the day of the week for each order, and then build a visualization that reveals how sales volumes shift across the week. The cookie sales dataset used here is a clear, relatable example, but the same techniques apply to any business data that includes a date column.

Understanding your date data

Before writing any formulas, it helps to confirm exactly what date information you're working with. In the Fields pane on the right side of the Power BI interface, locate and expand the Orders table.

The Orders table contains columns for Customer ID, Order ID, Product, Units Sold, Date, Revenue, Cost, and Profit.

  • The key column for this analysis is Date.
  • In Data view, each entry appears as a fully formatted date, such as "Saturday, February 1, 2020."
  • This rich date format is exactly what Power BI's DAX time intelligence functions need to work with.
  • The analysis goal is practical and directly useful: determine how many cookies are sold on each day of the week.
  • To answer this question, you first need to extract the day-of-week information from each date.
  • Store the day-of-week data as its own column, which the next step covers.

Creating a calculated "Day of week" column

A calculated column lets you add a new field to your table based on a DAX formula. Every row will automatically receive a value computed from that formula, and the column will update whenever your data refreshes. Follow the steps below to create a Day of week column using the WEEKDAY function.

Step 1: Switch to Data view and open Column tools

Make sure you are in the Data view; click the table icon on the left sidebar if needed. Once there, select the Column tools tab at the top of the screen to access column creation and formatting options.

Step 2: Create a new column

Click New column in the Column tools tab. The formula bar at the top of the screen will become active and ready for your input.

Step 3: Start building the formula

In the formula bar, type the name of your new column followed by an equals sign:

Day of week =

As you begin typing a DAX function, Power BI displays an autocomplete dropdown showing matching functions. For date-related work, you'll notice options such as DAY, NEXTDAY, and WEEKDAY. While DAY extracts the numeric day of the month, WEEKDAY is the function you need to identify which day of the week a date falls on.

Step 4: Use the WEEKDAY function

Type WEEKDAY( in the formula bar. A tooltip will appear showing the function signature:

WEEKDAY(Date, [ReturnType])

The WEEKDAY function returns a number from 1 to 7 that identifies the day of the week for a given date. The ReturnType argument controls which day is counted as day 1.

Step 5: Reference the Date column

Inside the WEEKDAY function, type Orders[Date]. As you type, a dropdown will appear listing available tables and columns, making it easy to select the correct field.

TipUsing the fully qualified reference Orders[Date] (table name plus column name) is a good habit. It makes formulas easier to read and avoids ambiguity when your model contains multiple tables with similarly named columns.

Step 6: Specify the return type

After Orders[Date], type a comma. The tooltip will display the available return type options:

ReturnTypeNumbering
1Sunday = 1, Saturday = 7
2Monday = 1, Sunday = 7
3Monday = 0, Sunday = 6

For this analysis, enter 1 so that Sunday is represented as 1 and Saturday as 7. Your complete formula should now read:

Day of week = WEEKDAY(Orders[Date],1)

Step 7: Confirm the formula

Press Enter to create the column. Power BI will calculate a value for every row in the Orders table and display the results immediately.

You'll now see a Day of week column filled with numbers from 1 to 7 alongside the original date values. You can cross-check the output by comparing a known date: for example, "Saturday, February 1, 2020" should show 7 using return type 1. You're ready to move on to visualization.

Visualizing orders by day of the week

With the Day of week column in place, you can now build a chart that makes the day-by-day pattern immediately visible to anyone reviewing the report.

Step 1: Switch to Report view

Click the report icon on the left sidebar to switch to Report view.

Step 2: Add the Day of week field to the canvas

In the Fields pane on the right, expand the Orders table and check the box next to Day of week. Power BI will automatically place a default visual, typically a bar chart, on the report canvas.

Step 3: Configure the axis

Drag the Day of week field to the Axis area of the visual in the Visualizations pane. This ensures that the x-axis represents days of the week (as numbers 1–7) and the y-axis represents the count or sum of orders for each day.

Step 4: Read the chart

The resulting bar chart displays a bar for each day value (1 through 7), with bar height reflecting the volume of orders on that day. Remember the mapping you chose: 1 = Sunday, 2 = Monday, 3 = Tuesday, and so on through 7 = Saturday.

Interpreting and communicating day-of-week patterns

Once your chart is rendered, spend a moment examining the shape of the data before sharing it with stakeholders.

Identifying spikes and dips

Look for bars that stand out noticeably above or below the average. In the cookie sales example, you may observe a clear spike on day 3 (Tuesday), with the remaining days showing comparatively lower volumes.

A spike like this is a meaningful business signal. It could indicate a weekly promotion, a restocking pattern, a delivery schedule, or simply organic customer behavior. When presenting this chart to stakeholders, lead with the observation ("Tuesday consistently shows the highest order volume") and then invite discussion about the possible cause rather than asserting a conclusion the data alone cannot confirm.

Tips for explaining the chart to non-technical audiences

When sharing a day-of-week chart, two common points of confusion are worth addressing proactively:

  • The x-axis shows numbers, not day names. Let your audience know up front that 1 = Sunday and 7 = Saturday (or whichever mapping you chose), so they can read the chart without constantly referring back to a legend.
  • The chart shows relative volume across days, not absolute totals in isolation. A "low" day might still represent a significant number of orders if the overall data set is large.
NoteThe numeric labels (1–7) on the axis are a direct result of how the WEEKDAY function returns its values. If your audience would prefer to see day names on the axis instead of numbers, you can create an additional calculated column that maps each number to its corresponding day name using a DAX SWITCH statement, then use that column as the axis field instead.

Further customization

The chart is already functional, but you can continue refining it to suit your reporting needs. The Filters and Fields panes remain accessible alongside the visual, and the Orders table can be expanded to bring in additional fields, such as Units Sold or Revenue, if you want to show more than just order counts per day.

TipConsider combining your day-of-week analysis with a slicer for product type or date range. This lets stakeholders interactively explore whether the Tuesday spike is consistent across all products or driven by a specific item, a much richer insight than a static chart alone can provide.
Topic 5

Text Functions and Product-Level Insights

When your data includes text-based fields like product names, you can use Power BI's text functions to extract meaning, create categories, and filter data in ways that simple numeric operations cannot achieve.

Rather than relying on manually maintained lookup tables, you can write DAX formulas that inspect the contents of a text column and automatically classify or count records based on what they find. This section walks you through two closely related techniques: creating a calculated column that labels products by ingredient using FIND and IF, and building a DAX measure that counts orders meeting multiple business conditions using CALCULATE and COUNTROWS.

Reviewing your product data before writing formulas

Before writing any text-based formulas, it helps to understand the shape of your product data so you know what patterns to search for.

  1. Switch to the Data view by clicking the data icon on the left sidebar.
  1. Locate the Product column in your data table. You will see product names such as "Chocolate Chip" listed across multiple rows.
  1. Scroll through the Product column to review the full range of product names. You will notice entries such as "Sugar" and "White Chocolate Macadamia" alongside the chocolate varieties.

This review tells you that "chocolate" appears in some product names but not all, and that it can appear at different positions within a name (e.g., at the start in "Chocolate Chip", or in the middle of "White Chocolate Macadamia"). This is exactly the scenario where a text-search function becomes valuable.

Creating a calculated column with FIND to detect a keyword

The FIND function searches for one text string inside another and returns the position at which the search text begins. If the text is not found, it returns an error by default, but you can supply a fallback value to avoid errors and make the result easier to work with downstream.

Step 1 — Add a new column

With your data table visible, click New column in the Column tools tab. The formula bar will activate, ready for you to enter a column name and formula.

Step 2 — Start the FIND formula

Name the column Has Chocolate and type the equals sign (=) followed by FIND(. Power BI will display the function tooltip showing its full syntax:

FIND(FindText, WithinText, [StartPosition], [NotFoundValue])

Step 3 — Specify what to search for and where

Enter "chocolate" as the first argument, followed by a comma. Then type Orders[Product] to tell the function to search within the Product column of the Orders table.

Has Chocolate = FIND("chocolate", Orders[Product]

Step 4 — Set the start position and not-found value

Add another comma, then type 1, 0 to start the search at position 1 and return 0 whenever "chocolate" is not found in the product name. This prevents errors from appearing in your column.

Has Chocolate = FIND("chocolate", Orders[Product], 1, 0)

The tooltip will highlight the [NotFoundValue] parameter as you type.

NoteThe FIND function is case-sensitive. If your product names use mixed casing, you may need to account for that in your formula. In this example the product names use title case, but the search string "chocolate" is lowercase; test your data carefully to confirm matches behave as expected.

Step 5 — Review the numeric output

After entering the formula, the Has Chocolate column will populate. Products that do not contain "chocolate" will show 0. Products that do contain "chocolate" will show a number representing the character position where the word begins, for example 1 for "Chocolate Chip" because "chocolate" starts at the first character.

Any value greater than 0 confirms the product name contains the word "chocolate". Products like "Chocolate Chip" show 1, while non-chocolate products like "Sugar" show 0.

Wrapping FIND with IF to create a readable business category

A column containing position numbers like 1 and 0 is functional, but not immediately meaningful to a business user reading a report. Wrapping the FIND result inside an IF statement converts the numeric output into a clear text label.

Step 1 — Open the IF function

In the formula bar, begin replacing the existing formula by typing if(. The IF function tooltip will appear showing its syntax.

Step 2 — Write the logical test

The logical test checks whether the FIND function returned a value greater than 0, which indicates "chocolate" was found in the product name:

if(FIND("chocolate", Orders[Product], 1, 0) > 0,

Step 3 — Define the TRUE and FALSE return values

Complete the formula by specifying what to display when the condition is true and when it is false:

  • If TRUE (the product contains "chocolate"): return "Has Chocolate"
  • If FALSE (the product does not contain "chocolate"): return "No Chocolate"

The complete formula is:

Has Chocolate = if(FIND("chocolate", Orders[Product], 1, 0) > 0, "Has Chocolate", "No Chocolate")

Step 4 — Apply the formula and verify the results

Press Enter to apply the formula. The Has Chocolate column will now display the text label "Has Chocolate" or "No Chocolate" for every row, making the category immediately readable.

Scroll through the table to confirm that products like "White Chocolate Macadamia" are correctly labeled as "Has Chocolate", even though the word "chocolate" does not appear at the start of the name.

TipThe IF function can be combined with additional functions for more complex classification logic. For example, you could nest multiple IF statements or use SWITCH to assign products to more than two categories.

The formula bar and data table remain visible at all times so you can review the applied logic as you work.

You now have a calculated column that automatically categorizes every product row based on its name. This column can be used as a filter, a slicer, or a legend in any visual in your report.

Building a DAX measure to count orders with multiple conditions

Calculated columns classify data row by row, but DAX measures go further by aggregating data across your entire table according to conditions you define. The CALCULATE function is the foundation for this kind of conditional aggregation. In this example, you will create a measure that counts the number of orders for the "Chocolate Chip" product where more than 500 units were sold.

Step 1 — Create a new measure

In the Fields pane on the right side of the Power BI Desktop interface, right-click on the Orders table. Select New measure from the dropdown menu.

Step 2 — Name the measure

In the formula bar, type the measure name followed by an equals sign:

Chocolate chip with over 500 units =

Choosing a descriptive measure name like this is a good habit: it makes the measure self-documenting when it appears in the Fields pane and in visuals.

Step 3 — Add the CALCULATE function

Type CALCULATE after the equals sign. The tooltip will appear explaining that CALCULATE "Evaluates an expression in a context modified by filters." This is the function that allows you to combine an aggregation with filter conditions.

Step 4 — Specify the aggregation with COUNTROWS

Inside CALCULATE, type COUNTROWS( and select the Orders table as the argument. The COUNTROWS function counts the number of rows in the table; in this context, that equates to the number of orders.

CALCULATE(COUNTROWS(Orders),

After closing the COUNTROWS parenthesis, add a comma to begin specifying the filter conditions.

Step 5 — Add the first filter condition

Type Orders[Units Sold]>500 to restrict the count to orders where more than 500 units were sold.

Step 6 — Add the second filter condition

Add a comma after the first filter, then type Orders[Product]=="Chocolate Chip" to further restrict the count to only the "Chocolate Chip" product. The complete measure formula is:

Chocolate chip with over 500 units = CALCULATE(COUNTROWS(Orders),
    Orders[Units Sold]>500, Orders[Product]=="Chocolate Chip")

Close the parentheses and press Enter to save the measure.

NoteBoth filter conditions are passed as separate arguments to CALCULATE, separated by commas. CALCULATE applies all filter conditions simultaneously, so only rows satisfying both conditions are counted.

Step 7 — Add the measure to a visual and verify the result

The new measure will appear under the Orders table in the Fields pane. Drag it into a visual, such as a card, to display the result. The value returned, for example 185, represents the total number of orders for "Chocolate Chip" with more than 500 units sold.

This single number answers a specific business question (how many high-volume Chocolate Chip orders exist in the dataset) without requiring any manual filtering or exporting to another tool.

Extending text functions for further product analysis

The techniques you have just applied (searching text with FIND, categorizing results with IF, and aggregating conditionally with CALCULATE and COUNTROWS) form a flexible toolkit for a wide range of product analysis scenarios. Here are examples of how you can extend this logic:

  • Filter for high-volume orders by category: Add the Has Chocolate calculated column as a filter condition in a CALCULATE measure to count or sum only chocolate product orders above a sales threshold.
  • Classify products by ingredient or type: Use the same FIND/IF pattern to create additional category columns, for example identifying "Sugar" cookies, "Macadamia" products, or any other keyword present in your product names.
  • Combine multiple text conditions: Nest additional IF statements or use the OR and AND functions to assign products to categories based on more than one keyword.
  • Use the category column as a slicer: Because the Has Chocolate column contains text labels, you can add it directly to a slicer visual, allowing report viewers to filter the entire report by product category with a single click.
TipWhen building measures that combine text filters with numeric thresholds, always verify the result against a filtered table view first. This helps you confirm that both conditions are working as intended before you publish the report.

You now have a practical foundation for turning raw product name data into structured categories and targeted business metrics using Power BI's text and DAX functions.
